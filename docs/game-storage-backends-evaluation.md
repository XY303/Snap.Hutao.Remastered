# 原神共存存储方案评估

评估日期：2026-11-03。此文是基于项目代码及上游文档的设计评估，不代表已经测试原神、游戏热更新或反作弊兼容性。没有创建、格式化或挂载虚拟磁盘，也没有修改真实游戏安装。

## 结论

值得优先试验的是 **同一个 ReFS 卷内的文件块克隆（写时复制）**，可用 VHDX 容纳该卷。它能让两个独立文件共享物理块，任一文件被写入时分配自己的块，解决硬链接“一边写入、两边都变”的主要风险。虚拟磁盘本身不自动去重；关键是内部文件系统及复制方式。

用户记忆中的“专用于高重复文件”的文件系统很可能是 **DwarFS**。它适合归档大量相似版本，但本身只读，作为需要更新、修复、热更新的游戏安装介质不如可写的块克隆直接。

## 方案比较

| 方案 | 重复数据处理 | 写入隔离 | 对当前项目的判断 |
| --- | --- | --- | --- |
| NTFS 硬链接 | 完全相同文件共用一个文件对象 | 无，写入会影响其他名字 | 当前实现；需要共存记录及解除/强行修复流程 |
| 单个 VHDX + NTFS | VHDX 仅封装卷，不自动去重 | 普通副本独立，硬链接仍共写 | 单独使用不能解决问题，增加挂载及容量管理 |
| 单个 VHDX + ReFS 块克隆 | 不同文件共用选定数据块 | 文件系统写时复制 | 最值得原型验证；必须显式确认块克隆成功 |
| 不可变基础 VHDX + 两份差分子盘 | 两服读取相同基础虚拟磁盘块，各写自己的子盘 | 虚拟磁盘层隔离 | 可行，但基础盘生命周期、磁盘标识、挂载、合并/重建链复杂 |
| DwarFS 镜像 | 面向高重复数据的去重压缩 | 基础镜像只读 | 适合只读历史版本/缓存；日常运行需要额外可写层或落盘 |
| Btrfs/ZFS | reflink、快照、块去重等 | 正确配置下可写时复制 | Linux 生态更直接；Windows 需额外文件系统实现/驱动，不宜作为通用默认方案 |
| Windows Server Data Deduplication | 后台识别并去除重复数据 | 由文件系统与过滤组件维护 | 是服务器功能，不能当作普通 Windows 11 开箱能力 |

## ReFS/VHDX 具体设计

初次从现有 NTFS 安装迁入 ReFS，需要实际复制一份基础资源，不能跨卷零成本克隆。验证期间保留原安装，还需预留这份基础资源的空间。

两服入口放在 **同一个挂载卷内的两个目录**；小文件保持各自副本。读取区服转换清单，仅对确认相同的资源建立块克隆，差异资源独立准备。不能把两个独立 VHDX 内部文件当作同卷文件直接克隆；外层宿主卷是 ReFS，也不等于内部 NTFS 文件天然支持 ReFS 块克隆。

Microsoft 文档说明，ReFS 克隆后的共享区域被写入时会分配新区域，文件之间保持隔离；源与目标必须处于同一 ReFS 卷，并满足簇对齐、Integrity Streams 设置等限制。显式使用 FSCTL_DUPLICATE_EXTENTS_TO_FILE 时还要处理单次范围长度等约束。

Windows 11 24H2 起，受支持的复制操作可原生使用块克隆，Dev Drive 也支持此能力。但 **不能只看到 File.Copy 成功就宣称去重成功**：应做能力探测，验证实际分配空间，并测试克隆后分别原位写入、截断、替换、内存映射写入时另一服的内容不变。当前代码明确限制 NTFS，不能简单去掉限制就声称支持 ReFS。

Dev Drive 有不同的过滤驱动/信任配置，微软不推荐在其上安装应用。普通 ReFS 与 Dev Drive 不应混为一谈；原神、官方启动器及反作弊都需要独立实测，不以块克隆技术可用推导游戏兼容。不要为测试关闭安全功能。

VHDX 管理还需要：稳定挂载路径、启动时挂载和权限处理、宿主与客体两层空间检查、增长和收缩策略、异常关机恢复、文件占用时禁止卸载、镜像移走后的清晰错误提示。动态 VHDX 的虚拟剩余空间不保证宿主物理盘有足够空间。

## DwarFS 与其他去重文件系统

DwarFS 的上游定位就是面向高重复数据的高压缩只读文件系统；Windows 版本通过 WinFsp 提供挂载，上游仍将 Windows 支持标记为实验性。若把两服内容放在同一镜像里，可利用跨文件冗余；将两份镜像分别压缩，不应假设能够跨镜像自动共享数据。

用于日常游戏时，配置、Persistent、日志、缓存和游戏更新都要写入。要么把可写内容放在镜像之外，要么加入独立的可写覆盖层；后者必须处理删除标记、改名、文件替换、内存映射和更新后的空间回收。只把已知 Persistent 目录移出去，不能证明所有游戏写入都被覆盖。镜像创建速度、随机读取延迟、解压 CPU 占用、覆盖层增长及反作弊兼容性都应测量。

Btrfs 提供 reflink 与去重基础接口；WinBtrfs 是额外的 Windows 驱动。ZFS 同样支持块克隆与去重，但自动去重会增加索引、CPU、内存和 I/O 成本；本项目已经有清单知道哪些资源相同，优先选显式块克隆通常比引入全盘自动去重更直接。实际收益应以两服资源样本测量，不能套用其他数据集的压缩率。

## 建议的验证顺序

1. 在临时、小型 ReFS 测试卷内验证两个文件的块克隆、物理空间和写入隔离，不接触真实游戏。
2. 验证同一 VHDX 挂载卷内双目录、重启挂载、两层空间不足和异常中断恢复。
3. 使用可恢复的测试客户端验证两服启动、内存映射读取、热更新、完整校验修复、官方启动器和反作弊。未通过前只标记实验性。
4. 另测 DwarFS 作为只读资源库/版本归档的空间收益和访问速度，再决定是否值得开发覆盖层。

本次只完成强行修复功能和上述评估，未实现新的 ReFS、DwarFS 或虚拟磁盘后端。
